# Audit de la plateforme C-Pay — 2 novembre 2026

Périmètre : dépôt `norbertm09/Cpay`, branche `develop` (commit `e8a536e`), version 2.7.0 déployée en production
(`c-pay.global`, 137.74.46.246) et en développement (`dev.c-pay.global`, 51.91.98.115). Méthode : quatre revues de
code indépendantes (backend, interfaces web, infrastructure et CI/CD, applications mobiles) avec vérification de
chaque constat dans le code et citation `fichier:ligne`, complétées par des contrôles transverses (visibilité du
dépôt, historique git, vulnérabilités des dépendances). Les rapports détaillés sont dans `docs/audit-2026-11-02/`.
Aucun test en conditions réelles chez les opérateurs n'a encore eu lieu : ce qui en dépend est marqué « à vérifier ».

Sévérités : **P0** bloquant le pilote · **P1** avant l'ouverture à des marchands · **P2** dette à planifier.

Verdict : le **cœur récent** (authentification unifiée, caisse, finalisation atomique, règlement, idempotence
durable, registre des capacités, chaîne de livraison) est de niveau B et sans défaut bloquant. Les risques se
concentrent dans **trois zones** : (1) les **routes historiques encore montées** dans le backend et la
**réconciliation MTN/Airtel**, qui s'appuie sur une fonction SQL non versionnée et un callback MTN qui ignore les
transactions marchandes ; (2) un **secret de base de données présent dans l'historique d'un dépôt public** ; (3) la
**publication mobile**, impossible en l'état (SDK cible refusé par Google Play, pas de suppression de compte, pages
légales inachevées).

Le pilote interne peut démarrer dès que les P0 transverse et backend sont traités (3 à 5 jours de travail) ; les
25 P1 forment le lot « ouverture marchands » ; les P2 s'étalent sur le trimestre.

## 4. P1 par domaine (avant ouverture aux marchands)

**Backend** (`01-backend.md`) : réponses 5xx ou illisibles des providers classées « refus » → fonds libérés
(`classifyRailResult`) ; webhook Airtel marchand sans frais, règlement ni pay-link (net 0) ; `/momo/payout` appelle
MTN dans la transaction SQL, `/momo/requesttopay` et `/momo/accountbalance` ouverts à tout porteur ; routes
historiques `/merchant/collect|disburse` = second moteur sans plafonds ni antifraude, trois barèmes de frais ;
routes admin `settlements/:id/complete|reject` sans journal, `/admin/settlement/run` factice.

**Portails** (`02-portails-vitrine.md`) : mot de passe forcé contournable par rechargement (marchand, porteur) ;
jeton admin en `localStorage` ; aucune CSP sur les SPA ; création marchand admin avec pays `CM` forcé, devise libre,
liste de pays hors périmètre sans CF/GQ ; injection HTML dans les rapports imprimés du portail partenaires.

**Infrastructure** (`03-infrastructure-cicd.md`) : dépôt public ; déploiement SSH en `root` sans commande forcée ;
sauvegardes ni hors serveur, ni chiffrées, ni testées, échec silencieux ; chaîne d'alerte incomplète
(`node-exporter`/`postgres-exporter` absents → 3 règles mortes, crons muets, certificat non surveillé) ; rollback
lent (même `CPLUS_TAG` entre releases, images écrasées) ; indisponibilité à chaque déploiement (builds sur la prod,
`compose up` recrée l'API, double déploiement main + tag) ; `restore-db.sh` et le runbook sourcent encore `.env`.

**Mobile** (`04-applications-mobiles.md`) : clé d'idempotence régénérée à chaque appui (double ordre sur reprise) ;
statut `unknown` des retraits affiché comme un succès ; cache Room en clair jamais purgé à la déconnexion ;
`DeepLinkActivity` exportée qui avale les liens `pay.c-pay.global` ; profil porteur, QR scan et « Décaisser »
hérités dans l'app marchande ; Expo : mode administrateur embarqué, non aligné sur la caisse (pays, référence).

**Suivi (2026-11-09, lot 2 livré)** : P1 backend 1 à 5 et P1 portails 1 à 5 corrigés — résultats 5xx/illisibles →
`unknown` (classifyRailResult, providers, normalize, orchestrateur) ; webhook Airtel marchand via `reconcileOne` +

## 5. P2 (dette, trimestre)

Fuite de messages internes (`err.message` en 500) et `console.*` hors Winston, secret d'URL de webhook dans les
logs ; rate limiting global appliqué aux callbacks ; pas de gestionnaire `unhandledRejection` ; détails fragiles

nginx 1.25), actions par tag majeur, angles morts CI, hôte sans `unattended-upgrades`, docs désalignées ;
Android : `FLAG_SECURE`, biométrie faible, build debug qui journalise les corps HTTP, R8 jamais éprouvé, chaînes
codées en dur, zéro test ; Expo : configuration de publication incomplète.

## 6. Points forts vérifiés

- Authentification unifiée (JWT 15 min `iss/aud`, refresh opaque haché avec rotation atomique et détection de
  réutilisation, cookies HttpOnly/Secure/Strict, verrouillage après 5 échecs, 2FA TOTP) ; aucune injection SQL.
- Webhooks fail-closed et idempotents (HMAC en temps constant, corps brut signé, claim atomique `status='pending'`).
- Cœur financier vague 4/6 : finalisation en une transaction, règlement sous verrou consultatif, réservation avant
  appel rail, statut `unknown` conservant les fonds, idempotence durable avec rejeu.
- Portails marchand et porteur : jeton en mémoire, refresh single-flight, verrous inter-onglets, intents financiers
  persistés et testés, confirmation forte partout ; vitrine sans `innerHTML` avec CSP stricte.
- Infrastructure : API non root avec `tini`, ports sur `127.0.0.1`, `/metrics` fail-closed, déploiement SSH natif
  avec `StrictHostKeyChecking`, sauvegarde bloquante avant migrations, environnements GitHub séparés, migrations
  rejouables sur base vierge testées en CI.
- Android : jetons dans `EncryptedSharedPreferences`, cleartext interdit, composants non exportés, refresh
  concurrent-safe, confirmation forte conforme, détection avec pays du marchand, mode hors ligne daté.
