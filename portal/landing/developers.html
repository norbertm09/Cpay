Démarrage rapide

Périmètre de lancement : les six pays de la CEMAC et la RD Congo. Moyens prévus : cartes bancaires, opérateurs de monnaie mobile et GIMAC. Les fonctions sont disponibles selon le pays et le service activés ; la connexion GIMAC est en cours d’intégration. La détection d’un numéro ne garantit pas la disponibilité d’un paiement.

Trois étapes séparent votre compte de votre premier lien de paiement. Un compte de niveau 0 suffit pour intégrer ; la vérification KYB n'est nécessaire que pour relever vos limites.

  1. Créez un compte marchand

    Sur merchant.c-pay.global/register. Le portail marchand est aussi l'endroit où vous suivez les paiements reçus par l'API.

  2. Créez une clé API dans le portail

    Portail marchand → Clés API → nouvelle clé avec les permissions voulues (pay_links, transactions). La clé et son secret ne sont affichés qu'une fois : stockez-les côté serveur, jamais dans un navigateur ou une application mobile.

  3. Créez votre premier lien de paiement

    Trois appels cURL ci-dessous : vérifier la clé, créer le lien, retrouver le paiement dans vos transactions.

Votre premier lien de paiement en trois appels

# 1. Vérifier la clé : la liste (vide ou non) de vos transactions répond 200
curl https://api.c-pay.global/api/v1/merchant/public/transactions?limit=1 \
  -H "X-API-Key: $CPAY_API_KEY" \
  -H "X-API-Secret: $CPAY_API_SECRET"

# 2. Créer un lien de paiement de 25 000 XAF valable 48 h
curl -X POST https://api.c-pay.global/api/v1/merchant/public/pay-links \
  -H "X-API-Key: $CPAY_API_KEY" \
  -H "X-API-Secret: $CPAY_API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "amount": 25000, "currency": "XAF", "description": "Facture INV-001", "expiresIn": 48 }'
# → 201 { "short_url": "https://pay.c-pay.global/AB12CD", "expires_at": "…", … }
#   Envoyez short_url à votre client (SMS, WhatsApp, e-mail) ou affichez-le en QR.

# 3. Retrouver le paiement une fois le client passé par la page
curl "https://api.c-pay.global/api/v1/merchant/public/transactions?status=authorized&limit=5" \
  -H "X-API-Key: $CPAY_API_KEY" \
  -H "X-API-Secret: $CPAY_API_SECRET"

Pour être prévenu sans interroger l'API, configurez un webhook : C-Pay appelle votre serveur à chaque paiement confirmé ou échoué.

Authentification et conventions

Les endpoints /merchant/public/* s'authentifient par clé API. Les endpoints de l'API Caisse utilisent la session du marchand (jeton Bearer). Toutes les requêtes et réponses sont en JSON.

En-têtes HTTP attendus
En-têteObligatoireRôle
X-API-Keyoui (routes publiques)Clé créée dans le portail marchand. Absente ou inconnue : 401 API_KEY_REQUIRED / 401 INVALID_API_KEY.
X-API-Secretoui pour les clés récentesSecret remis avec la clé. Les clés d'ancienne génération n'en ont pas ; les nouvelles le vérifient (401 INVALID_API_SECRET).
Idempotency-Keyrecommandé sur tout POST, obligatoire sur les opérations de caisse8 à 128 caractères, par exemple un UUID v4. Rejouer la même clé avec le même corps renvoie la réponse initiale ; la même clé avec un corps différent renvoie 409 IDEMPOTENCY_CONFLICT ; une requête identique encore en cours renvoie 409 IDEMPOTENCY_IN_PROGRESS. Longueur invalide : 400 INVALID_IDEMPOTENCY_KEY. Les clés sont conservées 24 h.
Content-Typeoui sur POSTapplication/json.
AuthorizationAPI Caisse uniquementBearer <access>, jeton de 15 minutes obtenu par POST /merchant/auth/login et renouvelé par /merchant/auth/refresh.
Base URL
https://api.c-pay.global/api/v1
Montants
Les exemples du lancement utilisent des montants entiers en XAF ou en CDF. Aucune conversion de change : la devise du client doit être celle du marchand.
Erreurs
Corps { "error": "message lisible", "code": "CODE_STABLE", "details?": … }. Codez sur code, pas sur error. Liste dans Codes d'erreur.
Permissions
Chaque clé porte ses permissions (pay_links, transactions, collect, disburse). Permission manquante : 403.
Limites de débit
Les points d'entrée publics sont limités en débit ; 429 avec les en-têtes RateLimit-* standard. POST /detect/phone : 30 requêtes par minute et par adresse.
Sécurité
N'appelez l'API que depuis votre serveur. Une clé exposée dans un navigateur ou une application mobile doit être révoquée immédiatement dans le portail.

POST /merchant/public/collect bientôt

Encaissement Mobile Money direct par clé API (demande de paiement poussée sur le téléphone du client). Corps prévu : amount, customerPhone, currency, description, reference. Cet endpoint répond aujourd'hui 410 FEATURE_DISABLED : il sera ouvert pays par pays au fil de l'activation des opérateurs. En attendant, les liens de paiement couvrent le même besoin, et l'API Caisse offre l'encaissement direct en session marchand.

API Caisse session marchand

Ces endpoints portent les opérations de caisse du portail marchand et de l'application Android : encaisser, retirer, transférer, suivre. Ils sont authentifiés par la session du marchand (Authorization: Bearer <access> obtenu via POST /merchant/auth/login, 15 minutes, renouvelé par /merchant/auth/refresh), pas par clé API. Ils conviennent à vos propres outils de caisse ; pour une intégration serveur, préférez les endpoints publics ci-dessus. Toute requête qui crée un mouvement exige Idempotency-Key.

Endpoints de l'API Caisse
EndpointRôle
GET /merchant/cash/summarySolde (available, pending, reserved), totaux du jour, limites et profil (niveau KYB, wallet, comptes bancaires).
POST /merchant/cash/collectEncaisser. amount, method (mobile_money ou card), customerPhone (requis en Mobile Money, opérateur détecté ; operator seulement pour sélectionner un service alternatif activé, par exemple Express Union), currency, description, reference. Mobile Money : 201 avec txnId, status: "pending", operator, fee, net, statusUrl. Carte : 201 avec payLink { shortId, shortUrl, expiresAt } si une passerelle carte est configurée, sinon 410 FEATURE_DISABLED.

Confirmation forte : l'objet confirm

Les retraits, les transferts wallet_to_bank et l'enregistrement du wallet exigent un objet confirm dans le corps. Son contenu dépend de la configuration du compte :

Contenu de l'objet confirm
CompteCorps attendu
Double authentification (TOTP) activée"confirm": { "code": "123456" } — code à 6 chiffres de l'application d'authentification
Sans double authentification"confirm": { "password": "…" } — mot de passe du compte

Objet absent ou invalide : 428 STEP_UP_REQUIRED { "methods": ["totp"] } ou ["password"], qui indique la méthode à présenter. Cinq échecs en 15 minutes : 429. Un ordre bank_to_wallet n'exige pas de confirmation : aucun fonds ne quitte le compte.

# Retrait de 50 000 vers le wallet enregistré (compte avec 2FA)
curl -X POST https://api.c-pay.global/api/v1/merchant/cash/withdraw \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Idempotency-Key: 2c1f6a1e-5e0b-4f7c-9a3d-8b2e4c6d1f0a" \
  -H "Content-Type: application/json" \
  -d '{ "amount": 50000, "description": "Caisse du soir", "confirm": { "code": "123456" } }'

# Transfert wallet -> banque (compte sans 2FA)
curl -X POST https://api.c-pay.global/api/v1/merchant/cash/transfers \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Idempotency-Key: 9d7e5c3a-1b2f-4e6d-8a0c-3f5b7d9e1a2c" \
  -H "Content-Type: application/json" \
  -d '{ "direction": "wallet_to_bank", "accountId": "<account_id>", "amount": 200000, "confirm": { "password": "…" } }'

Webhooks sortants

Déclarez une URL https:// dans le portail marchand (rubrique Webhooks) ; le secret de signature est affiché une seule fois à la création. À chaque changement de statut, C-Pay envoie un POST JSON signé en HMAC-SHA256. Les adresses privées ou non HTTPS sont refusées, les redirections ne sont pas suivies, le délai maximal est de 10 secondes et une réponse 5xx ou une erreur réseau déclenche jusqu'à 3 nouvelles tentatives (5 s puis 10 s).

En-têtes envoyés

Content-Type:      application/json
User-Agent:        CPay-Webhooks/1.0
X-CPay-Event:      payment.completed
X-CPay-Signature:  sha256=3f1a…c9        ← à vérifier
X-CPay-Timestamp:  2026-10-16T09:12:33.120Z   (informatif, non signé)
X-CPlus-Event:     payment.completed       (transition, sera retiré)
X-CPlus-Signature: sha256=3f1a…c9        (transition, sera retiré)

Les en-têtes X-CPlus-* sont conservés provisoirement pour les consommateurs existants et seront retirés au plus tôt 90 jours après annonce sur cette page. Nouvelles intégrations : n'utilisez que X-CPay-Signature.

Événements et corps

Événements du webhook marchand : payment.completed, payment.failed, webhook.test (même forme, txnId préfixé test-, envoyé par le bouton « Tester » du portail).

Vérifier la signature

signature = "sha256=" + hex(HMAC-SHA256(secret, corps brut)). Calculez sur le corps exactement tel qu'il est reçu (octets, pas une re-sérialisation JSON), comparez en temps constant, répondez 2xx rapidement puis traitez en asynchrone. Un même événement peut être livré plusieurs fois : dédupliquez sur txnId.

const crypto = require('crypto');
app.post('/cpay/webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const given = String(req.get('X-CPay-Signature') || '').replace(/^sha256=/, '');
  const expected = crypto.createHmac('sha256', process.env.CPAY_WEBHOOK_SECRET).update(req.body).digest('hex');
  if (given.length !== expected.length || !crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected))) {
    return res.status(401).end();
  }
  const event = JSON.parse(req.body);   // { event, txnId, reference, amount, currency, status, method, authCode, timestamp }
  res.status(200).end();                // puis traitement asynchrone, idempotent sur event.txnId
});
<?php
$raw = file_get_contents('php://input');
$given = preg_replace('/^sha256=/', '', $_SERVER['HTTP_X_CPAY_SIGNATURE'] ?? '');
$expected = hash_hmac('sha256', $raw, $secret);
if (!hash_equals($expected, $given)) { http_response_code(401); exit; }
$event = json_decode($raw, true);
http_response_code(200);

SDK & plugin

Les SDK encapsulent l'authentification, l'idempotence et la vérification des webhooks. Ils sont facultatifs : l'API s'utilise avec n'importe quel client HTTP.

SDK JavaScript / Node.js @c-pay/sdk 1.1.0

Pour Node.js 18+, côté serveur uniquement. Fournit CPayClient (liens de paiement, transactions) et CPayClient.verifyWebhook(), qui choisit le bon en-tête de signature pendant la transition.

npm install @c-pay/sdk

const { CPayClient } = require('@c-pay/sdk');
const cpay = new CPayClient({ apiKey: process.env.CPAY_API_KEY, currency: 'XAF' });
const link = await cpay.collection.payLink({ amount: 25000, description: 'Facture INV-001' });
console.log(link.short_url);

SDK PHP calculus-plus/cpay-sdk 1.1.0

PHP 7.4+, extensions cURL et JSON. Classe CPay\CPayClient (createPayLink, listTransactions, getTransaction) et exceptions CPayException portant le code de l'API.

composer require calculus-plus/cpay-sdk

use CPay\CPayClient;
$cpay = new CPayClient(getenv('CPAY_API_KEY'), ['currency' => 'XAF']);
$link = $cpay->createPayLink(25000, ['description' => 'Facture INV-001']);
echo $link['short_url'];

Les SDK 1.1.0 envoient X-API-Key mais pas encore X-API-Secret : utilisez-les avec une clé d'ancienne génération (sans secret) ou appelez l'API directement comme ci-dessus. Les sources sont remises par developers@c-pay.global si votre gestionnaire de paquets ne trouve pas encore le paquet.

Extension WooCommerce 2.7.0

Ajoute C-Pay comme moyen de paiement dans WooCommerce 6.0+ (PHP 7.4+). Encaissement Mobile Money et lien de paiement ; configuration avec votre clé API et votre secret ; webhook signé vérifié par l'extension.

SHA-256 : b71c8c66bdbc834dbb90fb56a60c0533e48448b07bc7f613d12abac272f5b89e

Télécharger (83 Ko) 
1. WordPress → Extensions → Ajouter → Téléverser l'archive
2. Activer, puis WooCommerce → Réglages → Paiements → C-Pay
3. Renseigner la clé API et le secret (portail marchand → Clés API)
4. Déclarer l'URL de webhook affichée par l'extension dans le portail marchand (rubrique Webhooks)

Sandbox

Un environnement de test est disponible sur demande : il n'est pas encore en libre-service. Écrivez à developers@c-pay.global en précisant votre cas d'usage, le pays visé et le type d'intégration (API, WooCommerce, Android). Nous revenons vers vous avec une clé de test, l'URL de base du bac à sable et les numéros de téléphone de test qui simulent un paiement confirmé, refusé ou expiré.

En production, le bouton Tester de la rubrique Webhooks du portail envoie un événement webhook.test signé à votre URL.
